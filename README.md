# 酒馆云同步（ST Sync）扩展

酒馆前端扩展。**两台酒馆各装一份**，通过一个自建中转服务交换整份备份。

它只调用酒馆已有的 HTTP 接口（生成备份 / 恢复备份），**不改动任何酒馆后端代码**，
也不依赖构建工具——三个文件丢进去就能用。

整体的两端同步方案见仓库根目录的 [README](../../README.md)，
中转服务本身见 [relay/README.md](../../relay/README.md)。

## 安装

把整个 `st-sync/` 文件夹放进两台酒馆的：

```
<SillyTavern>/public/scripts/extensions/third-party/st-sync/
```

刷新酒馆页面，在「扩展」面板（`#extensions_settings`）里就能看到**酒馆云同步**。

> 装完刷新后如果没出现，看浏览器控制台有没有 `[ST-Sync]` 开头的日志——
> 有的话是加载成功但面板位置不对，没有的话是文件路径放错了。

## 配置

| 字段 | 填什么 |
|---|---|
| 中转地址 | 你部署好的中转服务地址，`https://` 开头，结尾不要带 `/` |
| 访问令牌 | 中转服务首次启动时打进日志的那个令牌（**不是** `ADMIN_TOKEN`，见下） |
| 命名空间 | 默认 `A`，和中转服务上 `BOOTSTRAP_NAMESPACE` 一致 |
| 桶名 | 默认 `tavern`，一般不用动 |
| 本机标识 | **一台选 `local`，另一台选 `cloud`，必须不同** |

⚠️ **`访问令牌` 和 `ADMIN_TOKEN` 不是一回事。** 这里填的是中转服务**生成**、
首次启动时打进日志的那个命名空间令牌。`ADMIN_TOKEN` 是你自己编的、只在服务端用的管理令牌，
**任何情况下都不该填进扩展**。详细区别见根 README 的 2.5。

填完点「测试连接」，会告诉你令牌属于哪个命名空间、桶里现在有几个文件。

### 两台设备的标识为什么必须不同

中转服务上每台设备有**独立的一条道**（`devices/<标识>/`）。两台都填 `local` 的话：

- 两边往同一条道上写，互相覆盖；
- 而"找对面有没有更新"的逻辑会把自己过滤掉，于是**永远发现不了对方**。

表现出来就是"同步按钮点了没反应"。这个错了不会有任何报错提示，只能靠自己确认。

## 按钮

| 按钮 | 作用 |
|---|---|
| 测试连接 | 确认地址、令牌、命名空间都对 |
| 上传到中转 | 把本机数据打包上传，**不动本机数据** |
| 从中转恢复 | 拉对方的最新备份**覆盖本机**，会提示刷新页面 |
| 智能同步 | 先判断两边谁改了，再决定拉还是推 |

## 自动行为

- **打开页面时**（默认开）：判断对面的备份有没有更新——有就拉，本机有改动就推，
  两边都动过则走冲突策略。**这是唯一会自动拉取的地方。**
- **使用期间定时上传**（默认关，间隔 30 分钟）：**只传不拉**。
  刻意不在这里拉取，是因为恢复会整份替换数据并要求刷新页面，在你聊天中途这么干太扰民。

同步是**整份覆盖**，不做文件级合并。两边都改过同一段内容时，必然丢掉一份。

## 数据存在哪

设置存在 **localStorage 的 `st-sync:settings`**，刻意**不**用酒馆的 `extension_settings`。

原因：`extension_settings` 会写进 `settings.json`，而 `settings.json` 正是备份内容的一部分。
一旦从对面恢复备份，本机的中转地址、令牌、设备标识就会被对面的值覆盖掉——设备标识一乱，
整个同步就废了。这些本来就是"每台设备各自的"配置，不该跟着数据被同步过去。

**想彻底重置这个扩展**（比如换了中转服务、令牌填错乱了），在控制台执行：

```js
localStorage.removeItem('st-sync:settings');
location.reload();
```

## 排查

所有日志都带 `[ST-Sync]` 前缀，控制台里过滤这个就能看全。

| 现象 | 多半是 |
|---|---|
| 测试连接失败 | 地址写错、服务没跑、被浏览器跨域拦住（看控制台具体报错） |
| 「上传成功但恢复没反应」 | 酒馆的备份/恢复接口路径和扩展里写死的不一致，见下 |
| 点了同步没反应 | 两台设备的**本机标识填成一样了** |
| 恢复后界面没变化 | 正常，恢复是覆盖磁盘数据，必须刷新页面才生效 |

扩展顶部的 `ST_API` 写死了酒馆的备份接口路径：

```js
const ST_API = {
    download: { method: 'POST', url: '/api/users/backup' },
    restore:  { method: 'POST', url: '/api/backups/restore' },
};
```

**这两个接口在两个不同前缀下**（下载在 `/api/users/`，恢复在 `/api/backups/`），
别被路径前缀误导。已在 SillyTavern 1.18.0 官方镜像上实测确认。
换酒馆版本后如果失效，用 [`tools/probe-st-backup.md`](../../tools/probe-st-backup.md) 重新探测，
改这里即可。

恢复接口的 multipart 字段名在各版本间变过，扩展会按 `backup` → `file` → `upload` → `avatar`
的顺序试，第一个成功的记进设置的 `restoreField`，之后直接用。所以**第一次恢复可能慢一点**，正常。

## 已知限制

- 同步是整份覆盖，不做文件级合并。
- 恢复后需要刷新页面，酒馆内存里还是旧数据。
- 自动上传靠浏览器定时器，**只在页面开着时才跑**；iOS 上 App 被系统杀掉后就不跑了。
- 令牌以明文存在 localStorage 里，能访问你浏览器的人就能拿走它。
