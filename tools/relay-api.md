# 中转服务接口规格 —— 怎么让扩展接上你自己的存储

> **给谁读**：已经有自己的存储/中转（WebDAV、S3、群晖、自建 API、别的同步服务……），
> 想让「酒馆云同步」扩展直接接上去的人；或者想用别的语言重写一份中转的人。
>
> **为什么需要这份**：扩展**只会说这一套协议，没有任何适配层**。它不是通用网盘客户端，
> 拔不掉也换不了后端。所以让扩展接上你的存储只有两条路——**你的存储实现这套接口**
> （这份文档讲的就是这个），或者改扩展的网络层（`extension/st-sync/index.js`
> 第 600–852 行，都是集中的，但改完你就是自己维护一份 fork 了）。
>
> **参考实现**：本仓库的 [`relay/`](../relay)，Node + Express，`server.js` 约 460 行。
> 本文所有"必须/建议"的判断都来自实测和 `extension/st-sync/index.js` 里的真实调用，
> 不是照抄参考实现的设计。

---

## 0. 三分钟版

要让扩展能用，你的存储需要提供 **5 个 HTTP 接口**，外加三件必做的事：

| # | 接口 | 一句话 |
|---|---|---|
| 1 | `GET /v1/meta` | 报一下令牌属于哪个命名空间 |
| 2 | `PUT /v1/ns/{命名空间}/{桶}/{键}` | 收**原始字节流**存下来 |
| 3 | `GET /v1/ns/{命名空间}/{桶}/{键}` | 把字节吐回去，**最好支持 `Range`**（见第 5 节，这条决定快慢） |
| 4 | `GET /v1/ns/{命名空间}/{桶}` | 列出桶里所有文件（扩展靠它发现对面设备、清理旧快照） |
| 5 | `DELETE /v1/ns/{命名空间}/{桶}/{键}` | 删文件 |

外加四件必做的事（都在第 3 节）：

1. **跨域要放行**，且要处理 `OPTIONS` 预检。
2. **必须 HTTPS** —— 云酒馆是 https 页面，混合内容会被浏览器拦掉。
3. **令牌要能映射到命名空间，并且服务端必须做隔离**（越权回 403）。
4. **别给响应加缓存头**（`Cache-Control` / `ETag` / `Last-Modified`）——
   扩展不做缓存控制，加了会让它读到旧的 `latest.json`，表现成"对面明明传了却说没更新"这种
   极难查的静默失效。这条最反直觉，见 3.4。

`/admin/*`、邀请码、`BOOTSTRAP_*` 这些**一个都不用实现** —— 那是参考实现自己的管理便利，
扩展从不调用（详见第 6 节）。

## 1. 数据模型：命名空间 / 桶 / 键

三级，和 URL 一一对应：

```
/v1/ns/{命名空间}/{桶}/{键}
         ↑          ↑      ↑
        A        tavern   devices/local/latest.json
```

- **命名空间**：隔离单位。令牌绑定到某一个命名空间，服务端**必须**保证 A 的令牌读写不到 B（第 3 节）。
- **桶**：命名空间里的一个文件夹。扩展默认用 `tavern`，用户可以改。语义上就是"一个文件夹"。
- **键**：桶里的相对路径，**可以含 `/`**，就是磁盘上的相对路径。要按段校验，挡住 `..` 穿越。

落到磁盘上建议就是 `<数据根>/<命名空间>/<桶>/<键>`，这样最省事。

### 1.1 扩展固定使用的目录布局（兼容的硬要求）

扩展不看你的存储里别的东西，它只认这个形状：

```
{桶}/
  devices/
    local/                                  ← {设备} = 扩展面板里「本机标识」填的值
      latest.json                           ← 指针：最新那份快照叫什么、多大
      snapshots/
        20261003-142530.zip                 ← 备份包本体，文件名是时间戳
        20261003-091502.zip
    cloud/                                  ← 另一台设备，同结构
      latest.json
      snapshots/
        20261003-140011.zip
```

要点：

- **`{设备}` 由扩展决定，服务端不要校验、不要解释。** 用户填 `local` / `cloud` 这种字符串，
  两台必须不同。你的服务端只需要把它当路径的一段。
- **扩展靠"列目录"发现对面设备**，用的正则是 `^devices/([^/]+)/latest\.json$`
  （`index.js:2764`）。所以**列目录接口必须把 `key` 原样返回成相对桶的完整路径**，
  不能只给文件名基名 —— 只给基名的话扩展永远发现不了对面，表现是"同步没反应"。
- **旧快照清理**靠前缀 `devices/{设备}/snapshots/` + **按文件名字典序倒排**，
  保留最近 N 份（`index.js:2810`）。因为它认的是"文件名就是时间戳"这个约定，
  所以**别改文件名格式**：`YYYYMMDD-HHMMSS.zip`（本地时间）。

### 1.2 `latest.json` 的内容

这是扩展自己写的普通 JSON 对象，**你的服务端原样存、原样取就行，不要解析它**：

```json
{
  "device": "local",
  "createdAt": "2026-10-03T06:25:30.000Z",
  "fileName": "20261003-142530.zip",
  "size": 52428800,
  "sha256": "9f86d081884c7d65..."
}
```

> 扩展判断"对面更新了没有"用的是 `sha256`（`index.js:2732`），拿不到就退化用 `size:createdAt`。
> 所以 **`sha256` 是可选但有价值**的：你的上传接口回 `sha256`，扩展就写进 `latest.json`，
> 版本比对更准（第 2.2 节）。

## 2. 五个接口

所有接口都要求 `Authorization: Bearer {令牌}`，令牌无效回 **403**（不是 401，参考实现就是这么分的；
扩展只在乎 `res.ok`，所以 401/403 都不会出错，但 403 更贴合"令牌无效"）。

### 2.1 `GET /v1/meta`

只用于扩展的「测试连接」按钮（`index.js:3270`）。

**响应**（200，JSON）：

```json
{ "namespace": "A" }
```

扩展把它回显给用户："连接正常，令牌属于命名空间「A」"。
**这个字段是给用户看的**，用来确认自己的令牌和命名空间对得上。别省，省了用户看不到确认信息。

### 2.2 `PUT /v1/ns/{命名空间}/{桶}/{键}` —— 上传

**请求**：body 是**原始字节流**，不是 multipart、不是 base64、不是 JSON 包装。

- `Content-Type` 可能是 `application/zip`（备份包，几十到几百 MB）或 `application/json`（`latest.json`）。
- **不要给 body 设大小上限**。这是最容易踩的坑：反代默认值往往只有 1 MB（nginx
  `client_max_body_size`），一超就 413，而备份包必然超（见第 8 节）。

**响应**（200，JSON）：

```json
{ "ok": true, "size": 52428800, "sha256": "9f86d081884c7d65..." }
```

| 字段 | 必需 | 说明 |
|---|---|---|
| `size` | **必需** | 实际落盘字节数。扩展拿它写进 `latest.json`，还用它决定下载时走不走分片 |
| `sha256` | 建议 | 内容哈希。给了，扩展就拿它当版本标记；不给就退化用 `size:createdAt` |

**实现建议**：

- **同名覆盖是正常操作**：扩展会用同一个键反复 PUT（`latest.json` 每次同步都重写）。
  别因为"文件已存在"回 409 / 412，覆盖就完了。也**不要**每次生成新的键。
- **先写 `.tmp` 再 `rename`**。否则下游可能在写入过程中读到半截文件，
  把它当成一份完整备份拉走 —— 那是"恢复出一个坏包"级别的故障。

### 2.3 `GET /v1/ns/{命名空间}/{桶}/{键}` —— 下载

**请求**：普通 GET；或者带 `Range: bytes=起始-末尾`（闭区间，末尾含）要某一段。

**响应**：

- 不支持 Range 时：**200** + 完整字节 + `Content-Length`。
- 支持 Range 时：**206** + `Content-Range: bytes {起}-{止}/{总长}` + **精确的 `Content-Length`**。

**硬要求**：

1. **206 必须精确回那么多字节。** 扩展收到后会核对实际长度，对不上就判定这块坏了、
   换一条新连接重试（`index.js:704`）。注意它核对的是**实际收到的字节数**，不是你的响应头，
   所以响应头写对了但少发几个字节一样会挂。
2. **只认单段 Range。** `bytes=a-b` 这种。多段 Range（逗号分隔）可以不支持 ——
   扩展从不发多段，你可以当成没收到 Range 头处理（回 200 整份即可）。
3. **别把"支持不了 Range"做成错误。** 直接回 200 整份，扩展**会自动降级**成单条流式下载，
   慢但能用（`index.js:699`）。回 416 也行不通 —— 那会被当成真失败。
4. `Range` 的用法包括尾部请求 `bytes=-N`（见下面自测）。扩展目前只发 `bytes=a-b`，
   但支持全一点没坏处。

**为什么要支持 Range**：实测中转下行会被**按连接限速**，单条稳定只有 35–53 KB/s，
80 MB 的包要 25 分钟以上；而 6 条连接并发拉同一个文件，合计能到 0.5–3.2 MB/s。
扩展对 **≥ 8 MB** 的文件会切成 **1 MB 的块、6 条并发**去拉（`index.js:137-140`）。
**实现 Range = 十几倍的下载速度差**，不是可选项而是体验分水岭。

### 2.4 `GET /v1/ns/{命名空间}/{桶}` —— 列目录

注意**末尾没有键**，只有桶。这一条和 2.3 是同一个前缀，靠"末尾有没有东西"区分。

**响应**（200，JSON）：

```json
{
  "files": [
    { "key": "devices/local/latest.json",              "size": 231,     "mtime": 1759480000000 },
    { "key": "devices/local/snapshots/20261003-142530.zip", "size": 52428800, "mtime": 1759480000000 },
    { "key": "devices/cloud/latest.json",              "size": 238,     "mtime": 1759483000000 }
  ]
}
```

| 字段 | 必需 | 说明 |
|---|---|---|
| `files` | **必需** | 数组，没有文件就回 `[]`。扩展写的是 `json.files \|\| []`，所以回 `null` 或整个字段缺失**不会报错**，而是被**静默当成空桶** —— 表现就是"列目录成功但永远发现不了对面"，比报错更难查 |
| `files[].key` | **必需** | **相对桶的完整路径**，带 `/`。只给基名会让设备发现和快照清理全失效（见 1.1） |
| `files[].size` / `mtime` | 建议 | 扩展目前不用，但管理界面和排查用得上 |

**必须递归列全**，包括 `snapshots/` 子目录里的。参考实现返回的 `usage`（总用量）扩展不用，可选。

### 2.5 `DELETE /v1/ns/{命名空间}/{桶}/{键}`

**响应**：200 任何 JSON 都行。**404 也要能容忍**（扩展会忽略 404，`index.js:847`）——
比如并发删除、或者对方手动清过桶。别为了"文件不存在"回 500。

## 3. 跨域、鉴权、传输

### 3.1 跨域（CORS）—— 必须，且不止是放行

扩展跑在**酒馆页面的源**上，你的存储是另一个源，**必然跨域**。而且：

- 扩展带 `Authorization` 头 → **非简单请求，会发预检**。
- 扩展发 `Range` 头 → 同样触发预检。
- `PUT` / `DELETE` 方法 → 也触发预检。

所以**必须处理 `OPTIONS`**，并且回这几个头（照抄即可）：

```
Access-Control-Allow-Origin: *
Access-Control-Allow-Methods: GET,PUT,POST,DELETE,HEAD,OPTIONS
Access-Control-Allow-Headers: Authorization,Content-Type,Range
Access-Control-Max-Age: 86400
```

`OPTIONS` 请求本身**不要鉴权**，回 204 空响应即可。

> `Allow-Origin: *` 安全的前提是**用 Bearer 令牌而不是 Cookie** —— 没有 Cookie 就没有 CSRF 面。
> 如果你的存储是 Cookie 鉴权，这里必须收紧成白名单，**且要小心**：改成 Cookie 之后
> 跨域会变成"带着用户凭证的请求"，风险完全不同。
>
> 另外参考实现还回了 `Access-Control-Expose-Headers: Content-Length,X-Mtime,Content-Range,Accept-Ranges`。
> 严格说**不是必需的**（`Content-Length` 本来就是跨域安全可读的头，扩展也只读它做进度估算），
> 但建议照做，方便以后排查和扩展。

### 3.2 鉴权

- 所有 `/v1/*` 都要 `Authorization: Bearer {令牌}`。
- 令牌 → 命名空间 的映射由你决定（参考实现存 sha256，明文只在签发时给一次）。
- **服务端必须做隔离**：URL 里的 `{命名空间}` 和令牌所属的命名空间不一致时，**必须 403**。
  别指望扩展"只访问自己的" —— 扩展只是把用户填的命名空间拼进 URL（`index.js:613`），
  用户手滑填错、或者恶意构造，都会打到你的接口上。**这一层只能服务端挡。**
- **令牌比较要用定长比较**（`crypto.timingSafeEqual` 那一类），别用 `===`
  逐字符比 —— 那是可测的时序侧信道。参考实现是 `lib/auth.js` 的 `timingSafeEqualStr`。
- ⚠️ **参考实现没有限流、也没有失败锁定，配额也不强制。** 扩展不依赖这些，
  所以它们不是"兼容性"要求 —— 但**它们是安全要求**，见第 6 节末尾。你要不要加、加在哪一层，
  由你自己判断。

### 3.3 传输

**必须 HTTPS。** 云酒馆是 https 页面，浏览器的混合内容策略**不允许它去请求一个 http 的中转**，
表现是「测试连接」直接失败，而且报错信息不会明说是混合内容，很容易查错方向。

### 3.4 ⚠️ 别给响应加缓存头 —— 会静默搞坏同步

**这条很容易踩，因为给文件服务加缓存头是"优化"的直觉动作，而后果非常隐蔽。**

扩展**不做任何缓存控制**：它不设 `cache: 'no-store'`，也不加时间戳查询参数，
就是反复 GET 同一个 URL。能正常工作，靠的是**参考实现恰好没发任何缓存验证头**
（没有 `Cache-Control`、没有 `ETag`、也没有 `Last-Modified`，只有一个自造的 `X-Mtime`），
浏览器因此每次都真去网络拿。

所以你的实现**不要**给 `/v1/ns/...` 的响应加这些东西：

| 别加 | 加了会怎样 |
|---|---|
| `Cache-Control: max-age=...` / `Expires` | `latest.json` 被浏览器缓存住。**A 推了新备份，B 却一直说"云端没有更新"** —— 因为 B 读到的 `latest.json` 是缓存里的旧的 |
| `ETag` / `Last-Modified` | 同上，浏览器会拿它做条件请求，拿到 304 和缓存的旧内容 |

想显式表达也行，方向是**反过来**：给这些响应回 `Cache-Control: no-store`。

（要加缓存的话，注意受影响的不只是 `latest.json` —— 列目录接口的回包同样会被缓存，
那会让"发现对面设备"也一起失灵。真加了就只能改扩展加 `cache: 'no-store'`，
那就变成维护 fork 了。）

### 3.5 路径安全

键里含 `/`，所以路径要**逐段校验**：拒绝空段、`.`、`..`、以及编码绕过（`%2E%2E` / `%2F`）。
**落盘前再确认一次最终绝对路径仍在桶目录之内**，别只靠字符串处理。

## 4. 客户端的时间预算（照这个配反代和超时）

扩展这边的所有超时（`index.js:91-122`），你的实现和中间层要能配合：

| 场景 | 客户端上限 | 说明 |
|---|---|---|
| 普通请求（`/v1/meta`、列目录、删除、JSON 上传） | 60s | |
| **上传备份包** | `max(60s, 体积 ÷ 32 KB/s)` | **按体积算**。100 MB ≈ 53 分钟，150 MB ≈ 80 分钟 |
| 下载（单条流式） | 总 600s，**空闲 120s** | 空闲 = "多久没有新字节到达"才算死；只要字节还在来就一直续命 |
| 下载（分片，≥ 8 MB 的文件） | 每块 1 MB、6 并发、每块最多重试 3 次；每块空闲 120s、单片总上限 600s | 见第 5 节 |

⚠️ **上传那一行是重点**：因为浏览器不给上传进度，扩展只能"按最低可容忍速度估一个总预算"，
所以预算给得非常宽松。**反过来，你这条链路上任何一层都不能有"整体请求超时 60s"这类设定**，
否则大备份包必挂。具体说：

- nginx：`client_max_body_size` 默认 1 MB **必须改**（`client_max_body_size 0;` = 不限）；
  它的 `client_body_timeout`（默认 60s）是"两次读之间"的超时、不是整体，慢但在动不会挂，
  但别去动它；`proxy_read_timeout` / `proxy_send_timeout` 建议 300s 起。
- **Cloudflare 免费版单次上传上限 100 MB**，备份包超了就上传失败，别让它挡在中间。
- 自己写的反代/网关：别设置"整个请求最多 N 秒"。

## 5. 快慢的关键：Range 与限速

放在前面第 2.3 节讲过接口，这里讲**为什么值得做**：

- 实测**下行被按连接限速**：单条连接稳定 35–53 KB/s，且"实收 ÷ 用时"精确等于它报的速度，
  确认不是截断、不是带宽问题，就是限速本身。
- 80 MB 的包单条约 25 分钟；6 条并发合计 0.5–3.2 MB/s，**十几倍**。
- 所以扩展对 ≥ 8 MB 的文件自动切块并发拉，服务端这一侧**只需要支持单段 `Range` → 206**。

如果**不**支持 Range：会有一次 200 响应被主动取消（扩展发现不是 206 就不再读它），
然后降级成单条流式，慢但能完成。所以不会坏，只是慢十几倍。

## 6. 不需要实现的东西

扩展**从不调用**下列接口，别为了兼容去实现它们：

| 东西 | 是谁在用 |
|---|---|
| `POST /admin/namespace`、`/admin/invite`、`GET /admin/*` | 参考实现自己的管理接口，你不需要 |
| `GET /admin`（那个只读管理后台页面） | 同上，参考实现自带 |
| `POST /v1/invite/redeem`（邀请码） | 同上。你想给别人开命名空间，用什么方式都行 |
| `BOOTSTRAP_NAMESPACE` / `BOOTSTRAP_TOKEN` 环境变量 | 只是"平台上不方便开 shell"的初始化便利 |
| `usage` / `count` 这类统计字段 | 参考实现的列表接口顺便回的，扩展不用 |
| `X-Mtime` 响应头 | 同上 |
| 限流、失败锁定、配额强制、审计 | **参考实现一个都没做**，见下面 |

### 6.1 ⚠️ 参考实现没做的两件事（兼容不需要，但你要知道）

这两条**不影响能不能接上**，但影响"接上之后安不安全"，所以写在这里：

| 没做的事 | 后果 | 实际风险有多大 |
|---|---|---|
| **没有限流，也没有"错几次就锁住"** | 爆破令牌时服务端不会降速、不会拦 | **风险很低**：默认令牌是 `crypto.randomBytes(32)`（256 位），实际不可爆破。真出问题基本是**令牌泄漏**（贴群里、提交进 git、截图带出来），而这一层没有任何补救 —— 泄漏了只能重建命名空间 |
| **配额只是统计，不强制** | 任何**有效**令牌都能一直写，直到把磁盘写满 | **中等，且值得注意**：盘满了**整个服务一起挂**，连别的命名空间、连你自己的同步都一起挂。所以"给别人开命名空间"本质上是**信任** —— 对方能拖垮你的服务 |

想补的话方向很直接：令牌长度别缩水、别泄漏；对外只给可信的人；反代层（Caddy / nginx）
可以挂 `limit_req` / `limit_conn` 兜一层；真要防写满就加个每命名空间的使用量上限
（列表接口已经算了 `usage`，拿它判断即可）。

另外，扩展的**分发和更新**也和中转无关：扩展是从 `extension` 分支装的，中转是从
`relay` 分支部署的，两者互不影响。

## 7. 自测清单（照着 curl 一遍）

把 `{BASE}` 换成你的地址、`{NS}` 换成命名空间、`{TOKEN}` 换成令牌、`{BUCKET}` 换成桶（比如 `tavern`）。

```bash
TOKEN=你的令牌
BASE=https://你的域名
NS=A
BUCKET=tavern
AUTH="Authorization: Bearer $TOKEN"
```

**① 元信息**

```bash
curl -sS -H "$AUTH" "$BASE/v1/meta"
# 期望：{"namespace":"A"} 级别的东西，能看到自己的命名空间
```

**② 上传一个小文件，看有没有 size**

```bash
printf 'hello' > /tmp/h.txt
curl -sS -X PUT -H "$AUTH" --data-binary @/tmp/h.txt \
  "$BASE/v1/ns/$NS/$BUCKET/devices/probe/latest.json"
# 期望：200 + JSON 里有 "size":5
```

**③ 下载整份**

```bash
curl -sS -H "$AUTH" "$BASE/v1/ns/$NS/$BUCKET/devices/probe/latest.json"
# 期望：原样回 hello
```

**④ Range 分片（最关键的一条）**

```bash
curl -sS -i -H "$AUTH" -H 'Range: bytes=1-3' \
  "$BASE/v1/ns/$NS/$BUCKET/devices/probe/latest.json"
# 期望：HTTP/1.1 206 + Content-Range: bytes 1-3/5 + Content-Length: 3 + body 是 "ell"
# 回 200 说明没支持 Range：能用，但下载会慢十几倍（第 5 节）
```

**⑤ 列目录，看 key 是相对完整路径**

```bash
curl -sS -H "$AUTH" "$BASE/v1/ns/$NS/$BUCKET"
# 期望：files[] 里的 key 形如 "devices/probe/latest.json"（带斜杠的完整相对路径）
```

**⑥ 删除，并且再删一次要能容忍 404**

```bash
curl -sS -o /dev/null -w '%{http_code}\n' -X DELETE -H "$AUTH" \
  "$BASE/v1/ns/$NS/$BUCKET/devices/probe/latest.json"
# 期望：200 或 204

curl -sS -o /dev/null -w '%{http_code}\n' -X DELETE -H "$AUTH" \
  "$BASE/v1/ns/$NS/$BUCKET/devices/probe/latest.json"
# 期望：404 也行 —— 扩展会忽略它（别回 500）
```

**⑦ 越权必须被挡住**（如果你做了命名空间隔离）

```bash
curl -sS -o /dev/null -w '%{http_code}\n' -H "$AUTH" "$BASE/v1/ns/另一个命名空间/$BUCKET"
# 期望：403。回 200 说明隔离没做，任何人都能读写别人的数据
```

**⑧ 跨域预检**

```bash
curl -sS -i -X OPTIONS \
  -H 'Origin: https://酒馆的源' \
  -H 'Access-Control-Request-Method: PUT' \
  -H 'Access-Control-Request-Headers: authorization,range' \
  "$BASE/v1/ns/$NS/$BUCKET/x"
# 期望：204（或 200），且 Allow-Methods 含 PUT、Allow-Headers 含 Authorization 和 Range
```

**⑨ 大文件走一次（验分片真的能用）**

```bash
head -c 20000000 /dev/urandom > /tmp/big.bin        # 20 MB，≥ 8 MB 才会触发分片
curl -sS -X PUT -H "$AUTH" --data-binary @/tmp/big.bin \
  "$BASE/v1/ns/$NS/$BUCKET/devices/probe/snapshots/20261003-000000.zip"
```

**⑩ 最后用扩展本身验收**（真正的验收）

两台酒馆装好扩展、填上你的地址/令牌/命名空间 → 点「**测试连接**」→ 应该回
`连接正常，令牌属于命名空间「…」` → 然后在一台点「**上传到中转**」、另一台点「**从中转恢复**」。

出问题就看**扩展面板最下面那个运行日志**（有「复制全部」）：每一步请求、每个 HTTP 状态码、
每个错误原因都在里面。对比它和你的服务端访问日志，基本一眼能看出是哪一层不对。

## 8. 已知的坑（踩过的，按踩到的频率排）

| 现象 | 原因 |
|---|---|
| 上传 413 / 断在半路 | 反代有 body 上限（nginx 默认 1 MB）。改 `client_max_body_size 0;`。或者 CDN 有上限（**Cloudflare 免费版 100 MB**） |
| A 明明推了新备份，B 却总说"云端没有更新" | 你给响应加了缓存头（`Cache-Control` / `ETag` / `Last-Modified`），`latest.json` 是从浏览器缓存里读的（第 3.4 节） |
| 测试连接失败，但 curl 能通 | 跨域。漏了 `OPTIONS` 预检，或 `Allow-Headers` 里没写 `Authorization` / `Range` |
| 测试连接失败，且 curl 从服务器上能通 | 你用的是 http。云酒馆是 https 页面，**混合内容会被浏览器拦掉**，必须 HTTPS |
| 永远发现不了对面设备、同步没反应 | 列目录的 `key` 只给了文件名，没给相对桶的完整路径（第 1.1 / 2.4 节） |
| 下载极慢，几十 MB 要几十分钟 | 没实现 `Range`，扩展降级成单条流式了（第 5 节） |
| 下载报"分片长度不对"、反复重试 | 206 没精确回够字节数。响应头写对了但少发几个字节一样挂（第 2.3 节） |
| 恢复出一个坏包 | 上传没做"先写 .tmp 再 rename"，读到了半截文件（第 2.2 节） |
| 旧快照越堆越多 / 快照被误删 | 快照清理认"文件名是时间戳"这个约定（`YYYYMMDD-HHMMSS.zip`），改了文件名格式就会乱（第 1.1 节） |
| 别人的令牌能读我的数据 | 服务端没做命名空间隔离（第 3.2 节） |
